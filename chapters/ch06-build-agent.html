Abstract

You’ve learned how the ReAct loop works (Chapter 2), how context accumulates and compacts (Chapter 3), and how extensions customize behavior (Chapter 4). Now build it yourself. Starting from a 30-line Python loop using the raw Anthropic Messages API, this chapter progressively adds tool dispatch, subagents, compaction, skills, and hooks, then assembles a complete agent — a task graph, worktree isolation, a teammate protocol, and error recovery — proving that Claude Code’s sophistication grows from a trivial core and that every later mechanism layers on without touching the loop. Based on the open-source Learn Claude Code course by shareAI.

6.1 The Loop Is 30 Lines

Every concept from Chapter 2 — the message array, tool calls, tool results, the “text or tool call?” decision — compiles down to this:

import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-4-20250514"
SYSTEM = "You are a coding assistant. Use tools to complete tasks."

TOOLS = [{
    "name": "bash",
    "description": "Run a shell command and return its output.",
    "input_schema": {
        "type": "object",
        "properties": {"command": {"type": "string"}},
        "required": ["command"],
    },
}]

def run_bash(command: str) -> str:
    import subprocess
    result = subprocess.run(command, shell=True, capture_output=True, text=True)
    return result.stdout + result.stderr

def agent_loop(query: str):
1    messages = [{"role": "user", "content": query}]

    while True:
        response = client.messages.create(
            model=MODEL, system=SYSTEM, messages=messages,
            tools=TOOLS, max_tokens=8000,
        )
2        messages.append({"role": "assistant", "content": response.content})

3        if response.stop_reason != "tool_use":
            return response.content[0].text  # Done — final text response

        # Execute tool calls, collect results
        results = []
4        for block in response.content:
            if block.type == "tool_use":
                output = run_bash(block.input["command"])
                results.append({
                    "type": "tool_result",
5                    "tool_use_id": block.id,
                    "content": output,
                })
6        messages.append({"role": "user", "content": results})
1
messages is the agent’s entire memory — one list of turns that every step appends to. There is no hidden state; the whole agent is “what’s in this list.”
2
Append the assistant turn before acting on it — the reply (including its tool_use blocks) must already be in history, or the tool_result you send next has nothing to attach to and the API rejects it.
3
The “text or tool call?” decision — stop_reason == "tool_use" is the API signalling the model wants to run a tool. Any other stop reason means it’s answering, so the loop returns.
4
One assistant turn can hold several blocks — the model may request multiple tools (and interleave text) in a single response, so you iterate rather than handling just one.
5
tool_use_id ties each result back to its call — with parallel tool calls in one turn, this id is how the model knows which result answers which request.
6
The write-back — feeding results back as a new user turn is what makes the loop self-sustaining. Omit this one line and the model never sees what its tools did.

That’s a complete autonomous agent. It reads files, runs tests, installs packages, and self-corrects — because the while True loop keeps spinning until the model decides it’s done.

The write-back step — appending tool results as a new user message — is the single most important line. Without it, the model never sees what happened. With it, the loop is self-sustaining.

6.2 Adding Tools Without Changing the Loop

A single bash tool is powerful but dangerous. The next step is a dispatch map — a dictionary routing tool names to handler functions:

from pathlib import Path

WORKDIR = Path(".")

def safe_path(p: str) -> Path:
    """Prevent directory escape."""
1    path = (WORKDIR / p).resolve()
2    if not path.is_relative_to(WORKDIR):
        raise ValueError(f"Path escapes workspace: {p}")
    return path

def run_read(path: str, limit: int = None) -> str:
    text = safe_path(path).read_text()
    lines = text.splitlines()
    if limit and limit < len(lines):
        lines = lines[:limit]
3    return "\n".join(lines)[:50_000]

def run_write(path: str, content: str) -> str:
    safe_path(path).write_text(content)
    return f"Written: {path}"

def run_edit(path: str, old_text: str, new_text: str) -> str:
    p = safe_path(path)
    text = p.read_text()
    if old_text not in text:
4        return f"ERROR: old_text not found in {path}"
5    p.write_text(text.replace(old_text, new_text, 1))
    return f"Edited: {path}"

# The dispatch map — add tools here, never touch the loop
TOOL_HANDLERS = {
6    "bash":       lambda **kw: run_bash(kw["command"]),
    "read_file":  lambda **kw: run_read(kw["path"], kw.get("limit")),
    "write_file": lambda **kw: run_write(kw["path"], kw["content"]),
    "edit_file":  lambda **kw: run_edit(kw["path"], kw["old_text"], kw["new_text"]),
}
1
.resolve() collapses .. and symlinks into a real absolute path — you can’t safety-check a path until it’s been normalized.
2
The actual escape guard — after resolving, confirm the path is still inside WORKDIR; this is what stops read_file("../../etc/passwd").
3
Truncate tool output to a token budget — a single huge file could blow the context window, so the read is capped (here ~50k chars) before it ever reaches the model.
4
Return an error string, don’t raise — the model reads this like any other tool result and can self-correct (re-read, fix the old_text), whereas an exception would kill the loop.
5
replace(..., 1) edits only the first match — the count 1 makes the edit surgical, so duplicate text elsewhere in the file isn’t clobbered.
6
Each handler adapts the model’s JSON args (**kw) to a plain function — adding a tool means adding one line here (and its schema to TOOLS); the loop never changes.

The loop’s tool execution block becomes:

for block in response.content:
    if block.type == "tool_use":
1        handler = TOOL_HANDLERS.get(block.name)
2        output = handler(**block.input) if handler else f"Unknown tool: {block.name}"
        results.append({
            "type": "tool_result",
            "tool_use_id": block.id,
            "content": output,
        })
1
Route by the name the model chose — block.name is whatever tool the model asked for; .get looks it up in the dispatch map instead of a hard-coded if/elif chain.
2
Unknown tools degrade to a message, not a crash — if the model hallucinates a tool name, it gets a “Unknown tool” string back and can try again; the loop survives.

The loop itself never changes. You add capabilities by adding entries to TOOL_HANDLERS and corresponding schemas to TOOLS. This is why the course’s tagline is “Bash is all you need” — the loop structure established in s01 carries the entire 19-chapter curriculum.

6.3 Subagents as Context Boundaries

Chapter 4 explained that subagents get their own context window. Here’s what that means in code:

def run_subagent(task: str) -> str:
    """Spawn a child agent with fresh context. Return only its final answer."""
1    child_messages = [{"role": "user", "content": task}]

    while True:
        response = client.messages.create(
            model=MODEL, system=SYSTEM, messages=child_messages,
2            tools=TOOLS, max_tokens=8000,
        )
        child_messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason != "tool_use":
            # Return ONLY the final text — discard all intermediate context
3            return response.content[0].text

        results = []
        for block in response.content:
            if block.type == "tool_use":
                handler = TOOL_HANDLERS.get(block.name)
                output = handler(**block.input) if handler else f"Unknown: {block.name}"
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": output})
        child_messages.append({"role": "user", "content": results})
1
A fresh array is the whole point — child_messages starts empty, so the child’s exploration never enters the parent’s context. This is the “context boundary.”
2
The child is handed tools without a task/spawn tool — that omission is what prevents a subagent from spawning subagents forever.
3
Only the final text crosses back — the parent receives this one summary; every intermediate file read and command the child ran is discarded when the function returns.

The subagent is the same loop with child_messages = [] — a fresh context. It might read 10 files and run 5 commands, but the parent only sees the final summary. All intermediate tool calls and results are discarded when the function returns.

This is the “disposable scratch pad” pattern: fresh context in, short summary out. The parent’s message array stays lean.

6.4 Context Compaction

Chapter 3 explained that context fills up and gets compressed. Here’s the implementation — a multi-lever approach:

def count_tokens(messages: list) -> int:
    """Approximate token count."""
1    return sum(len(str(m)) // 4 for m in messages)

def micro_compact(messages: list, keep_recent: int = 6) -> list:
    """Replace old tool results with one-line placeholders."""
    if len(messages) <= keep_recent:
        return messages
    compacted = []
    for i, msg in enumerate(messages):
2        if i < len(messages) - keep_recent and msg["role"] == "user":
            # Check if it's a tool result
            content = msg.get("content", "")
            if isinstance(content, list) and any(
                item.get("type") == "tool_result" for item in content
            ):
                compacted.append({
                    "role": "user",
3                    "content": "[Previous tool results compacted]"
                })
                continue
        compacted.append(msg)
    return compacted

def full_compact(messages: list) -> list:
    """Use the LLM itself to summarize the conversation so far."""
    transcript = "\n".join(str(m) for m in messages)
4    summary = client.messages.create(
        model=MODEL,
        messages=[{"role": "user", "content":
            f"Summarize this agent conversation. Preserve: "
            f"(1) what was accomplished, (2) current state, "
            f"(3) what remains to do.\n\n{transcript[:50000]}"
        }],
        max_tokens=2000,
    ).content[0].text

5    return [{"role": "user", "content":
        f"[Session compacted. Summary of prior work:]\n{summary}\n\n"
        f"Continue from where you left off."
    }]
1
A tokenizer-free estimate — len(str(m)) // 4 uses the rough “~4 characters per token” rule so the check is instant and needs no API call just to measure size.
2
Only old turns are touched — everything within the last keep_recent messages is left intact; compaction never rewrites the recent context the model is actively using.
3
Swap bulky tool output for a stub — micro-compaction is the cheap lever: it drops the content of old tool results while keeping the conversation’s shape (lossy, but no LLM call).
4
Full compaction is a separate LLM call — when micro-compaction isn’t enough, the model is asked to summarize its own transcript, preserving done/current/remaining.
5
Replace the entire history with one summary turn — the returned list is a single message; the agent resumes from the summary and never knows the old turns existed.

Integrated into the loop:

def agent_loop(query: str):
    messages = [{"role": "user", "content": query}]

    while True:
        # Compaction check before each API call
1        if count_tokens(messages) > 50_000:
            messages = full_compact(messages)
        else:
2            messages = micro_compact(messages)

        response = client.messages.create(...)
        # ... rest of loop unchanged
1
Two levers, picked by size — only past a token threshold do you pay for the expensive LLM summarization (full_compact); below it, the cheap lever is enough.
2
Micro-compaction runs every turn — trimming old tool results is constant background maintenance, so context grows slowly and the costly full pass is rarely needed.

This is exactly the mechanism from Chapter 3’s “compaction is lossy compression” — now visible as code. The agent doesn’t even know it happened; it just sees a summary of prior work and continues.

6.5 Skills: Lazy-Loading Knowledge

Chapter 4 explained skills as on-demand knowledge packs. The implementation uses a two-layer architecture:

Layer 1 — cheap directory in the system prompt (~100 tokens per skill):

class SkillLoader:
    def __init__(self, skills_dir: Path):
        self.skills = {}
        for skill_file in skills_dir.glob("*/SKILL.md"):
            text = skill_file.read_text()
            # Parse YAML frontmatter
1            _, frontmatter, body = text.split("---", 2)
            meta = yaml.safe_load(frontmatter)
2            self.skills[meta["name"]] = {
                "description": meta["description"],
                "body": body.strip(),
            }

    def get_directory(self) -> str:
        """Layer 1: names + descriptions for system prompt."""
        lines = ["Available skills:"]
        for name, skill in self.skills.items():
3            lines.append(f"  - {name}: {skill['description']}")
        return "\n".join(lines)

    def load_skill(self, name: str) -> str:
        """Layer 2: full body, loaded on demand via tool call."""
        skill = self.skills.get(name)
        if not skill:
            return f"Unknown skill: {name}"
4        return f"<skill name=\"{name}\">\n{skill['body']}\n</skill>"
1
Split a SKILL.md into header + body — the maxsplit of 2 separates the leading ---, the YAML frontmatter, and the rest, while leaving any --- inside the body untouched.
2
Store description and body separately — the description is the cheap part shown to every prompt; the body is the expensive part held back until needed.
3
Layer 1 — the directory — only name: description lines (≈100 tokens total) go into the system prompt, so the model knows skills exist without paying to load them.
4
Layer 2 — the full body — returned only when the model calls load_skill, so a skill’s full instructions cost tokens exactly when they’re relevant and never otherwise.

Layer 2 — full content loaded via a load_skill tool when the model decides it needs it:

TOOL_HANDLERS["load_skill"] = lambda **kw: skill_loader.load_skill(kw["name"])

The model sees “Available skills: deploy, db-migration, lecture-notes…” in every prompt. When the user says “deploy to staging,” the model calls load_skill("deploy") and gets the full procedure — consuming tokens only when relevant.

6.6 Hooks: Deterministic Control Outside the Loop

Chapter 4’s hooks fire at named moments. The implementation reads from a config file and runs shell commands:

import subprocess, os, json

def load_hooks(path: str = ".hooks.json") -> dict:
    if not Path(path).exists():
        return {}
    return json.loads(Path(path).read_text()).get("hooks", {})

def run_hooks(event: str, context: dict, hooks_config: dict) -> dict:
    """Run all matching hooks for an event. Returns {blocked, messages}."""
    result = {"blocked": False, "block_reason": "", "messages": []}

    for hook in hooks_config.get(event, []):
        matcher = hook.get("matcher")
1        if matcher and matcher != context.get("tool_name"):
            continue  # Doesn't match this tool

2        env = {
            **os.environ,
            "HOOK_EVENT": event,
            "HOOK_TOOL_NAME": context.get("tool_name", ""),
            "HOOK_TOOL_INPUT": json.dumps(context.get("tool_input", {})),
        }

3        proc = subprocess.run(hook["command"], shell=True, env=env,
                              capture_output=True, text=True)

4        if proc.returncode == 1 and event == "PreToolUse":
            result["blocked"] = True
            result["block_reason"] = proc.stderr or "Blocked by hook"
5        elif proc.returncode == 2:
            result["messages"].append(proc.stderr)

    return result
1
A hook can scope to one tool — if its matcher names a tool, it only fires for that tool; otherwise it’s skipped. This is how a “lint on edit” hook ignores bash calls.
2
Context crosses to the hook through env vars — the loop has no idea what the hook does; it just hands over event/tool/input as environment variables, the universal shell interface.
3
A hook is an arbitrary shell command — defined entirely in .hooks.json, outside this code, so policy is configured rather than programmed.
4
Exit code 1 on PreToolUse = veto — a non-zero exit before the tool runs blocks it (e.g. a security check refusing a dangerous command); stderr becomes the reason shown to the model.
5
Exit code 2 = inject a message, don’t block — the hook can feed advice back into the conversation while still letting the tool run.

In the loop:

# Before tool execution
pre = run_hooks("PreToolUse", {"tool_name": block.name, "tool_input": block.input}, hooks)
1if pre["blocked"]:
    output = f"BLOCKED: {pre['block_reason']}"
else:
    output = handler(**block.input)
2    run_hooks("PostToolUse", {"tool_name": block.name, "tool_output": output}, hooks)
1
The veto gate — if a PreToolUse hook blocked the call, the handler is never invoked; the model simply receives “BLOCKED: …” as the tool result and adjusts.
2
PostToolUse fires only after a successful run — it sees the output (for logging, formatting, follow-up checks) but can’t un-run the tool; the loop body itself stays untouched.

The loop doesn’t know what the hooks do — it just calls them at the right moments. A lint hook, a security check, a logging hook — all configured externally, zero context cost.

6.8.1 A task graph the agent can plan against

Once an agent does multi-step work, “what’s left, and what’s blocked?” needs a durable home outside the context window. A task is a small record on disk; dependencies are just a list of other task ids that must finish first:

from dataclasses import dataclass, asdict
import json
from pathlib import Path

TASKS_DIR = Path(".tasks"); TASKS_DIR.mkdir(exist_ok=True)

@dataclass
class Task:
    id: str
    subject: str
    status: str            # pending | in_progress | completed
    owner: str | None
    blockedBy: list[str]   # ids that must be completed first

def _path(tid): return TASKS_DIR / f"{tid}.json"
1def load_task(tid): return Task(**json.loads(_path(tid).read_text()))
def save_task(t): _path(t.id).write_text(json.dumps(asdict(t), indent=2))

def can_start(tid: str) -> bool:
    """Runnable only when every blocker exists and is completed."""
2    return all(_path(d).exists() and load_task(d).status == "completed"
               for d in load_task(tid).blockedBy)

def claim_task(tid: str, owner: str = "agent") -> str:
    task = load_task(tid)
3    if task.status != "pending":  return f"{tid} is {task.status}"
    if not can_start(tid):        return f"{tid} is still blocked"
    task.owner, task.status = owner, "in_progress"
    save_task(task)
    return f"Claimed {tid} ({task.subject})"

def complete_task(tid: str) -> str:
    task = load_task(tid); task.status = "completed"; save_task(task)
    unblocked = [t.subject for p in TASKS_DIR.glob("task_*.json")
4                 if (t := load_task(p.stem)).status == "pending" and can_start(t.id)]
    return f"Completed {tid}" + (f" — unblocked: {unblocked}" if unblocked else "")
1
A task is just a JSON file — load/save are one line each because the “database” is the .tasks/ directory; this is what lets state survive a restart and be shared between agents.
2
can_start is a pure dependency check — a task is runnable only when every id in its blockedBy exists and is completed. No scheduler, just all(...) over the blockers.
3
Claiming is guarded twice — already-claimed or still-blocked tasks are refused, so two agents reading the same directory can’t both grab the same work.
4
On completion, report what was unblocked — the walrus := loads each pending task once and re-checks can_start; the returned list is exactly the signal a teammate needs to pick up newly-available work without being told.

The graph is just files. can_start is a pure dependency check, and complete_task reports which tasks its completion unblocked — which is exactly the signal an autonomous agent (or a teammate) needs to pick up the next available work without being told.

6.8.2 Worktrees: real isolation for parallel work

When more than one agent edits the same repo, a shared working tree is a data-loss hazard — one agent’s checkout yanks the files out from under another. Git worktrees give each branch its own directory. The agent gets a tool that wraps git worktree add, plus strict name validation, because the name becomes a filesystem path:

import re, subprocess
WORKTREES_DIR = Path(".worktrees"); WORKTREES_DIR.mkdir(exist_ok=True)
1VALID_NAME = re.compile(r'^[A-Za-z0-9._-]{1,64}$')

def create_worktree(name: str, task_id: str = "") -> str:
2    if not VALID_NAME.match(name or ""):
        return f"Error: invalid worktree name '{name}'"
    path = WORKTREES_DIR / name
    if path.exists():
        return f"Worktree '{name}' already exists"
3    r = subprocess.run(["git", "worktree", "add", str(path), "-b", f"wt/{name}", "HEAD"],
                       capture_output=True, text=True)
    if r.returncode != 0:
        return f"Git error: {r.stderr.strip()}"
4    if task_id:
        t = load_task(task_id); t.worktree = name; save_task(t)
    return f"Worktree '{name}' created at {path}"
1
A strict whitelist, because the name becomes a path — it’s used as both a directory and a branch name, so anything outside [A-Za-z0-9._-] (or longer than 64) is rejected up front.
2
Validate in the tool, before git ever sees the name — the safety boundary lives here, not in hoping git rejects a malicious value afterward.
3
List-form subprocess (no shell=True) — passing args as a list avoids shell injection entirely, and -b wt/{name} gives each worktree its own branch off HEAD.
4
Bind the task to its sandbox — recording worktree on the task is how the graph above knows which isolated checkout each piece of work owns.

Note where the validation lives: in the tool, before git ever sees the name — not relying on git to reject something afterward. Removal is the mirror image, and deliberately refuses to delete a worktree with uncommitted changes unless forced (discard_changes=true) or explicitly kept for review. The agent now has a safe place to do parallel work; the task graph above records which sandbox each task owns.

6.8.3 Subagents, with the safety boundary wired in

The subagent from Section 6.3 returns in the full system, but now it runs tool calls through the same permission and hook layer as the parent, and caps its own iterations so a confused child can’t spin forever:

Isolation of context and enforcement of policy are independent: the child gets its own message array, but not its own rules.

6.8.4 Teams and a plan-approval protocol

Multiple long-lived agents need two things the subagent pattern lacks: a way to message each other, and a way to gate an action on another agent’s approval. The message bus is one append-only inbox file per agent:

class MessageBus:

        inbox = MAILBOX_DIR / f"{to}.jsonl"
1        with open(inbox, "a") as f:

                                "type": msg_type, "metadata": metadata or {}}) + "\n")

        inbox = MAILBOX_DIR / f"{agent}.jsonl"
        if not inbox.exists(): return []
        msgs = [json.loads(l) for l in inbox.read_text().splitlines() if l.strip()]
2        inbox.unlink()

1
Append-only JSONL, one message per line — the inbox is a file each agent appends to; "a" mode plus a trailing newline means senders never overwrite each other, no message broker required.
2
Read-once: reading drains the mailbox — unlink() deletes the inbox after it’s read, so each message is delivered exactly once and the file doesn’t grow unbounded.

A protocol layers request/response semantics on top of raw messages. Each request gets an id; a reply is only valid if it references a pending request of the matching type — so one approval can’t accidentally satisfy a different pending ask:

@dataclass
class ProtocolState:
    request_id: str; type: str; sender: str; target: str; status: str; payload: str

pending_requests: dict[str, ProtocolState] = {}

def request_plan(teammate: str, task: str) -> str:

1    pending_requests[rid] = ProtocolState(rid, "plan_approval", "lead", teammate, "pending", task)
2    BUS.send("lead", teammate, f"Submit a plan for: {task}", "plan_request", {"request_id": rid})
    return f"Asked {teammate} to plan {task} (request {rid})"

def match_response(response_type: str, request_id: str, approve: bool):
    state = pending_requests.get(request_id)
3    if not state or not response_type.startswith(state.type):
        return                                 # wrong request or wrong type — ignore
    state.status = "approved" if approve else "rejected"
1
Each ask is tracked by a unique id — pending_requests records the outstanding request so a later reply can be correlated back to it; raw messages alone have no request/response semantics.
2
The request_id rides along in metadata — the teammate echoes it in their reply, which is how the lead matches an approval to the exact thing it asked about.
3
A reply only counts if id and type match — this guard stops one approval from accidentally satisfying a different pending request; mismatches are silently ignored rather than acted on.

This is the spine of the “orchestrator + teammates” pattern from Chapter 13: the lead spawns teammates, asks for a plan, and waits for explicit approval before any teammate touches files — all expressed as messages on disk, with no special infrastructure.

6.8.5 Surviving the real world: error recovery

A loop that runs for hours will hit rate limits (429), overloaded servers (529), and prompts that grow past the context window. Production agents wrap every model call in a retry policy with exponential backoff and jitter, and escalate when a class of error repeats:

def retry_delay(attempt: int) -> float:
1    base = min(BASE_DELAY_MS * (2 ** attempt), 32_000) / 1000
2    return base + random.uniform(0, base * 0.25)

def with_retry(fn, state: RecoveryState):
    for attempt in range(MAX_RETRIES):
        try:
3            result = fn(); state.consecutive_529 = 0; return result
        except Exception as e:
            name, msg = type(e).__name__.lower(), str(e).lower()
            if "ratelimit" in name or "429" in msg:               # transient → wait
                time.sleep(retry_delay(attempt)); continue
            if "overloaded" in name or "529" in msg:              # repeated → fail over
                state.consecutive_529 += 1
                if state.consecutive_529 >= MAX_CONSECUTIVE_529 and FALLBACK_MODEL:
4                    state.current_model = FALLBACK_MODEL
                time.sleep(retry_delay(attempt)); continue
5            raise
    raise RuntimeError("Max retries exceeded")
1
Exponential backoff, capped — the delay doubles each attempt (2 ** attempt) but min(..., 32_000) ceilings it at 32s so retries don’t drift into minutes.
2
Jitter prevents a thundering herd — adding a random fraction means many agents that hit a limit at once don’t all retry on the same beat and re-collide.
3
Success resets the failure counter — one good call clears consecutive_529, so the fallback logic only triggers on sustained overload, not a single blip.
4
Repeated 529s fail over to a cheaper model — when the primary model stays overloaded, switch to FALLBACK_MODEL to keep making progress instead of stalling.
5
Unknown errors are re-raised, not swallowed — only the error classes you understand are retried; anything else propagates so a real bug isn’t silently masked as “transient.”

The companion case is the prompt that’s simply too long. Rather than crash, the loop catches that specific error once, runs a reactive compaction to summarize old turns, and retries — the same lossy-compression idea from Section 6.4, now triggered by failure instead of a token threshold. Note the discipline in the except: transient errors are retried, a recurring class triggers a model fallback, and anything unrecognized is re-raised rather than silently swallowed.

6.8.6 The loop that ties it together

Here is the final agent_loop, stripped to its skeleton. Read it against the 30-line loop from Section 6.1 — it is the same shape, with each new mechanism slotted into the cycle at the point where it belongs:

def agent_loop(messages: list, context: dict):
1    tools, handlers = assemble_tool_pool()
    state = RecoveryState()

    while True:
2        for job in consume_cron_queue():
            messages.append({"role": "user", "content": f"[Scheduled] {job.prompt}"})
3        inject_background_notifications(messages)
4        prepare_context(messages)

        try:
            response = call_llm(messages, context, tools, state)   # wrapped in with_retry
        except Exception as e:
5            if is_prompt_too_long_error(e):

            raise

        messages.append({"role": "assistant", "content": response.content})
        if not has_tool_use(response.content):
6            trigger_hooks("Stop", messages)
            return

        results = []
        for block in response.content:
            if block.type != "tool_use":
                continue
7            if blocked := trigger_hooks("PreToolUse", block):
                output = str(blocked)
8            elif should_run_background(block.name, block.input):
                output = start_background_task(block, handlers)
            else:
                output = call_tool_handler(handlers.get(block.name), block.input, block.name)
                trigger_hooks("PostToolUse", block, output)
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": output})

9        messages.append({"role": "user", "content": build_user_content(results)})
1
MCP folds in here — builtin tools and every external MCP server’s tools are merged into one tools/handlers pool, so the loop treats a remote tool exactly like a local one.
2
Cron enters as an ordinary user turn — scheduled jobs are just appended to messages as [Scheduled] …; the model can’t tell them apart from a human request, so no new code path is needed.
3
Background tasks report back the same way — a finished detached task injects its result as a message; async work re-joins the conversation as plain context.
4
Context prep happens before the call — compaction and the tool-result budget (everything from Section 6.4) run here so the request is always within limits.
5
Reactive compaction on a too-long prompt — instead of crashing, catch that one error, summarize old turns in place (messages[:]), and continue to retry. Compaction triggered by failure, not a threshold.
6
The Stop hook is the “are we really done?” gate — before returning, a hook can inspect the state and decide the agent isn’t actually finished, sending it back around.
7
Permission + policy sit between request and execution — the walrus := both runs the PreToolUse hooks and captures a veto; if blocked, the handler is skipped and the block reason becomes the result.
8
Slow tools detach instead of blocking — build/pytest/install return a placeholder immediately and finish in the background (their output arrives later via annotation 3).
9
Still the write-back — after every surrounding mechanism, the final line is the same one from Section 6.1: results go back as a user turn. The 30-line core wasn’t replaced, it was surrounded.

Everything is here, and nothing has displaced the core. Cron and background notifications enter as ordinary user turns. Context preparation and recovery wrap the model call. Permission, background routing, and hooks sit between “the model asked for a tool” and “the tool ran.” And the last line is still the write-back — the single most important line from Section 6.1. The 30-line loop didn’t get replaced; it got surrounded.

6.8.7 …and the rest

For brevity this section skipped several subsystems that follow the identical “layer on, don’t restructure” rule. Each is a handful of functions:

Mechanism What it adds Where it plugs in
Background tasks slow tools (build, pytest, install) return a placeholder immediately; real output arrives later as a task_notification the should_run_background branch in the loop
Cron durable cron-expression jobs persisted to disk; a scheduler thread fires them consume_cron_queue at the top of the loop

None of it is surprising once you’ve internalized the loop. Each subsystem is a small, self-contained module that the loop calls at a well-defined moment — which is the whole thesis of this chapter, demonstrated at scale.

6.9 Key Takeaways

  • A complete autonomous agent is a while True loop that sends messages, executes tool calls, and appends results — 30 lines of Python
  • The write-back step (appending tool results as a user message) is the single most important line — it’s what makes the loop self-sustaining
  • Tools are added via a dispatch map (TOOL_HANDLERS dict), never by modifying the loop
  • Subagents are the same loop with messages = [] — fresh context, return only the final answer
  • Compaction summarizes old messages when tokens exceed a threshold — the agent doesn’t know it happened
  • Skills load full knowledge on-demand via a tool call, keeping the system prompt lean
  • Hooks run shell commands at named moments (PreToolUse, PostToolUse) with zero context cost
  • A complete agent reassembles every mechanism — task graph, worktrees, teams + approval protocol, error recovery, background, cron, MCP — into one program, and the core is still the same loop
  • Durable state (tasks, jobs, transcripts) lives on disk as files, so it survives restarts and is shared between agents without special infrastructure
  • Isolation of context (subagents, worktrees) and enforcement of policy (permission, hooks) are independent layers — a fresh context still obeys the same rules
  • Every feature layers on without changing the core loop — the 30-line foundation carries the entire system
